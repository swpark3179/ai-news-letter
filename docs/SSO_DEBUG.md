# SSO 로그인 디버깅 — 「로직 문제인가, 변수 로드 문제인가」

로그인이 안 될 때 원인이 두 층으로 나뉘는데, 화면에는 똑같이 보입니다.

| | 무엇 | 화면에 나오는 것 |
|---|---|---|
| **A. 변수 로드** | 배포에 값이 없거나, 값을 넣었지만 빌드에 박힌 옛 값이 돌고 있다 | `SSO_TRAY_NOT_RUNNING` · `SSO_CONFIG_MISSING` |
| **B. 연동 로직** | 변수는 정상인데 트레이 통신·복호화 규격·등록 대조가 어긋난다 | `SSO_TRAY_NOT_RUNNING` · `SSO_DECODE_FAILED` · `SSO_NOT_REGISTERED` |

`SSO_TRAY_NOT_RUNNING` 하나가 양쪽에 다 걸려 있는 것이 문제의 핵심입니다. 브라우저는
「모듈이 안 떠 있다」와 「인증서를 못 믿는다」와 「주소가 틀렸다」를 구분해 주지
않습니다 — 셋 다 열리기 전 `close`/`error` 로만 나타납니다.

그래서 순서를 화면으로 굳혀 두었습니다.

```
/login/diag
```

운영에서는 `SSO_DEBUG_TOKEN` 을 설정하고 `/login/diag?token=<값>` 으로 엽니다.
관리자 세션이 살아 있는 브라우저라면 토큰 없이도 열립니다. 개발·스테이징
(`NODE_ENV != production`)은 그냥 열립니다.

---

## 4단계

각 단계는 **바로 앞 단계가 깨끗할 때만 의미가 있습니다.** 순서가 곧 진단입니다.

### 0단계 — 브라우저에 실린 값

`NEXT_PUBLIC_` 값은 빌드 시점에 코드로 박힙니다. 여기 보이는 것이 화면이 실제로
쓰는 값입니다. 배포 환경변수와 다를 수 있습니다.

로그인 화면에서 한 번 시도한 뒤 돌아오면 **그 시도의 결과와 상관 ID** 가 함께
보입니다 (`sessionStorage` 에 한 건만 남습니다 — 탭을 닫으면 사라집니다).

### 1단계 — 서버 변수 · 세션 · DB

「변수 로드」 문제는 전부 이 단계에서 걸러집니다. 확인하는 것:

| 항목 | 무엇을 잡아내나 |
|---|---|
| `build-sync` | **빌드에 박힌 값 vs 지금 프로세스의 값.** 다르면 재배포하지 않은 것입니다 — 가장 흔한 「변수 로드」 문제 |
| `tray-url` | 비어 있음 · `ws://`(혼합 콘텐츠로 차단) · URL 로 해석 안 됨 · 로컬 호스트가 아님 |
| `tray-app-code` | 비어 있음 · 레거시 교육포털 코드(`KCC60TRAY0109`)를 그대로 씀 |
| `decode-key` | `SSO_DECODE_KEY` 가 32바이트로 되돌려지는지 (8진 이스케이프·base64 둘 다 받음) |
| `unverified-gate` | **운영 빌드의 실 모드가 여기서 멈춥니다** — `SSO_ALLOW_UNVERIFIED_PAYLOAD` |
| `auto-create` | 미등록 EPID 가 403 인지 자동 가입인지 |
| `session-secret` | 없음(운영은 500) · 32자 미만 |
| `session-cookie` | 없음 / **있는데 검증 실패**(배포 사이에 `SESSION_SECRET` 이 바뀐 것) / 유효 |
| `cookie-secure` | 운영 빌드의 secure 쿠키를 http 로 받는 조합 — 로그인은 200 인데 다음 요청에서 로그아웃 |
| `supabase-url` · `supabase-key` · `members` | 등록 대조가 가능한 상태인지 (스키마 미적용 · 프록시 · 행 0개) |

값은 **마스킹**해서 나옵니다. 복호화 키·서비스 롤 키·세션 시크릿은 존재 여부와
길이만 담기고, 식별자는 `KN****13` 형태로 접힙니다.

### 2단계 — 트레이 핸드셰이크

트레이 모듈에 직접 물어보고 **오간 것을 순서대로** 남깁니다. 로그인 화면은 실패를
5종으로 접어 보여 주지만, 접는 과정에서 사라지는 것이 디버깅에 필요한 것들입니다.

- 소켓이 **열렸는지** — 열리기 전 실패면 「모듈 미실행」과 「인증서 불신」이 같아진다
- `close` code — `1006` 은 핸드셰이크 실패(모듈·포트·TLS), `1000` 은 정상 종료 후 무응답
- 규격 밖이라 **조용히 버려진 프레임**과 그 이유 (production 은 계속 기다립니다)
- 각 단계까지 걸린 시간

판정은 `parseTrayFrame` 을 그대로 씁니다 — 진단이 production 과 다른 규칙으로
판단하면 의미가 없습니다.

프레임 원문(암호문)은 기본적으로 가려져 있고, 체크박스로 펼칩니다. 화면을 공유
중이라면 켜지 마세요.

목업 모드에서는 붙을 트레이가 없으므로 목업 페이로드를 만들어 3단계로 넘깁니다.

### 3단계 — 서버 디코딩 드라이런

실제 로그인과 **같은 경로**(복호화 → 관문 `assertDecodedUser` → `members` 대조)를
밟되 **세션을 발급하지 않습니다.** 실제 라우트와 다른 점은 둘뿐입니다.

1. 무결성 게이트를 지나쳐서라도 디코딩을 시도합니다. 운영에서 게이트에 막혀 있으면
   「무엇이 문제인지」를 알 방법이 게이트 메시지밖에 없기 때문입니다. 이때 결론은
   「실제 로그인은 게이트에서 막힌다」로 표시되고 쿠키는 만들어지지 않습니다.
2. `members` 를 **읽기만** 합니다. EPID 백필·자동 가입은 「일어날 것」으로만 알립니다.

가장 중요한 출력은 **전략표**입니다.

| 결과 | 뜻 | 어디를 고치나 |
|---|---|---|
| `adopted` + 클레임 키 | 이 전략으로 EPID 까지 얻었다 | 끝. 규격이 확정되면 이 전략만 남긴다 |
| `no-epid` + 클레임 키 | 복호화는 됐고 **필드 이름만 다르다** | `toDecodedUser` 의 후보 목록에 키 추가 |
| `unreadable` | 복호화 결과가 텍스트·클레임이 아니다 | 「단순 인코딩」 가정이 틀렸다 → `SecuBase` 규격 필요 |
| `skipped` | 시도조차 못 했다 (키 미설정 등) | **환경변수 문제** — 이유가 함께 나옵니다 |

`no-epid` 로 클레임 키가 찍히면 규격 문의 없이 그 자리에서 끝납니다. 전부
`unreadable` 이면 담당자에게 물어야 하는 상황이고, 그 표가 곧 질문의 근거입니다
([SSO_KNOX_PROTOCOL.md](SSO_KNOX_PROTOCOL.md) 의 질문 목록).

각 단계에 **복사** 버튼이 있습니다. 담당자에게 그대로 붙여 넣을 수 있는 텍스트로
나옵니다.

## 「로그인은 됐는데」를 가리는 방법

증상이 「로그인이 되는 것 같은데 화면이 계속 /login 으로 돌아간다」거나 「로그인
후에 값이 안 보인다」면 순서가 다릅니다.

1. `/login?force=1` 에서 실제로 한 번 시도합니다.
2. `/login/diag` 의 **0단계**에서 그 시도의 결과와 상관 ID 를 확인합니다.
3. **1단계를 다시 실행**해 `session-cookie` 항목을 봅니다.

| `session-cookie` | 뜻 | 다음 |
|---|---|---|
| 유효 | **로그인 자체는 통과했습니다** | SSO 가 아니라 권한·데이터 쪽 (`members.role` · `is_admin`) |
| 있는데 검증 실패 | 배포 사이에 `SESSION_SECRET` 이 바뀌었다 | 값을 되돌리거나, 쿠키를 지우고 다시 로그인 |
| 없음 | 쿠키가 저장되지 않았다 | 같은 단계의 `cookie-secure` 항목 |

## 화면 없이 — 서버 로그

로그인 시도마다 상관 ID 가 붙은 한 줄이 남습니다. 응답 헤더
`x-sso-trace-id` 와 본문 `traceId` 도 같은 값입니다.

```
[sso 7fckwrsm] 디코딩 실패: … { gate: 'blocked', attempts: [ … ] }
[sso a1b2c3d4] 등록되지 않은 사용자 — 종류 knox · 게이트 open · 채택 wb64-plain · 시도 2건
```

전략별 결과가 그 줄에 함께 붙어 있어, 진단 화면을 열지 않고도 같은 내용을 확인할
수 있습니다. 사용자가 화면에서 읽어 주는 여덟 글자로 해당 줄을 찾습니다.

운영 응답 본문에는 상세를 싣지 않습니다 — 어느 전략이 왜 실패했는지가 그대로
나가면 페이로드 위조의 힌트가 됩니다.

## 열어 두는 범위

| | 진단 화면·API |
|---|---|
| 개발 · 스테이징 | 그냥 열림 |
| 운영 + 관리자 세션 | 열림 |
| 운영 + `SSO_DEBUG_TOKEN` 일치 | 열림 (헤더 `x-sso-debug-token` 또는 `?token=`) |
| 운영 + 그 밖 | 403 |

세션을 요구하지 않는 것이 요점입니다 — 진단해야 하는 상황이 곧 로그인이 안 되는
상황이라, 로그인을 요구하면 쓸 수 없습니다.

토큰은 임의값이면 됩니다.

```bash
node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"
```

`?token=` 은 히스토리·리퍼러에 남으므로, 화면에서 API 를 부를 때는 헤더로 보냅니다.
진단이 끝나면 토큰을 지우고 재배포하는 편이 깔끔합니다.

## 관련 파일

```
src/app/login/diag/          진단 화면 (page.tsx · DiagClient.tsx)
src/app/api/auth/sso/diag/   GET 스냅샷 · POST 드라이런 (세션을 만들지 않는다)
src/lib/auth/sso/
  diagnostics.ts             환경변수·DB 확인 · 접근 통제 · 드라이런  ("server-only")
  diag-types.ts              진단 자료구조 · 텍스트 변환 (서버·화면 공용)
  probe.ts                   트레이 핸드셰이크 관찰 (브라우저)
  shape.ts                   페이로드 모양 분석 — 값을 드러내지 않고 규격만 추정
  last-attempt.ts            마지막 로그인 시도 기록 (sessionStorage)
  decode-knox.ts             전략 루프 + 추적(DecodeTrace) — 규격이 오면 이 파일만 고친다
```
